# 外部研究与开源参考

## 1. 文档状态

- 调研日期：2026-08-12
- 对应阶段：阶段 0 至阶段 3 技术准备
- 用途：记录能够约束实现的外部证据，不替代本项目真机实验

本文优先采用 Apple 官方文档、原始论文、数据集发布页和作者维护的代码仓库。博客、论坛与二手摘要不作为工程或算法结论的主要依据。

## 2. Apple 平台资料

### 2.1 Core Motion

主要来源：

- [Core Motion 框架](https://developer.apple.com/documentation/coremotion)
- [CMMotionManager](https://developer.apple.com/documentation/coremotion/cmmotionmanager)
- [Getting raw accelerometer events](https://developer.apple.com/documentation/coremotion/getting-raw-accelerometer-events)
- [Getting raw gyroscope events](https://developer.apple.com/documentation/coremotion/getting-raw-gyroscope-events)

直接结论：

1. 使用单一 `CMMotionManager` 管理应用的运动服务。
2. 在开始前分别检查加速度计、陀螺仪和设备运动是否可用，不能由设备型号推定接口一定可用。
3. 连续保存原始数据应使用带队列与回调的 push API，避免依赖界面定时器轮询。
4. 请求采样频率高于硬件上限时，Core Motion 会使用设备实际支持的最大值，所以“请求间隔”和“实际间隔”必须同时记录。
5. 加速度计原始值以重力加速度为单位；本项目在平台适配层转换成米/秒²。陀螺仪原始角速度为弧度/秒。
6. 原始角速度可能受到温度等偏置影响；设备运动数据提供经过融合与偏置处理的旋转、重力、用户加速度和姿态。因此研究工具应保留原始来源，同时把设备运动作为独立来源保存。
7. 不同 Apple 设备坐标轴有明确方向，原始设备坐标必须保留；左右手镜像和佩戴方向标准化属于后续派生输入层。

对工程的影响：

- `ResearchMotionSample` 区分传感器来源并允许不同来源拥有独立时间戳；
- Core Motion 适配器不得把不同回调伪装成严格同步样本；
- 采样质量统计以实际回调间隔为依据；
- Simulator 数据必须标记为合成来源，不能参与真机数据质量结论。

### 2.2 Watch Connectivity

主要来源：

- [Watch Connectivity 框架](https://developer.apple.com/documentation/watchconnectivity)
- [Transferring data with Watch Connectivity](https://developer.apple.com/documentation/watchconnectivity/transferring-data-with-watch-connectivity)

直接结论：

1. `updateApplicationContext` 适合只保留最新状态，会覆盖传输管线中的旧上下文，不适合逐场原始数据事实传输。
2. `transferUserInfo` 提供排队的后台字典传输；`transferFile` 适合完整研发采集文件。
3. `sendMessage` 用于双方可达时的即时通信，不可作为离线可靠同步的唯一机制。
4. 系统接管后台传输后，接收应用可以在非活跃状态收到数据。
5. watchOS 后台任务必须在处理完成后显式结束。
6. Apple 官方样例明确要求使用真实配对的 iPhone 和 Apple Watch 验证文件传输与后台行为。

对工程的影响：

- 核心同步协议与 `WCSession` 适配器分离；
- Simulator 只验证传输状态机、校验、去重和失败重试，不宣称验证真实后台交付；
- 手表在手机确认完整接收前保留本地副本；
- 原始高频样本使用文件批次，不使用大量即时消息。

### 2.3 HealthKit 运动会话

主要来源：

- [Running workout sessions](https://developer.apple.com/documentation/healthkit/running-workout-sessions)
- [HKWorkoutSession](https://developer.apple.com/documentation/healthkit/hkworkoutsession)
- [HKLiveWorkoutBuilder](https://developer.apple.com/documentation/healthkit/hkliveworkoutbuilder)
- [Build a workout app for Apple Watch](https://developer.apple.com/documentation/healthkit/build-a-workout-app-for-apple-watch)
- [Building a multidevice workout app](https://developer.apple.com/documentation/healthkit/building-a-multidevice-workout-app)

直接结论：

1. Apple Watch 运动会话会针对运动调整传感器行为，并产生高频心率数据。
2. `HKWorkoutSession` 与 `HKLiveWorkoutBuilder` 是开始、暂停、继续、结束和最终保存正式运动的标准基础。
3. 会话与 builder 都通过后台队列 delegate 报告状态、样本和错误，界面层不能直接承担状态机。
4. Apple Watch 同时只能运行一个主运动会话；另一个运动开始时必须处理明确错误。
5. 正式运动应该在产生运动事实的手表侧创建和保存。
6. Apple 的多设备运动样例同样要求真实设备验证。

对工程的影响：

- 阶段 4 将建立独立 `WorkoutSessionService`，不把 HealthKit 代码放进 SwiftUI 页面；
- 正式运动状态机需要覆盖授权拒绝、另一运动占用、暂停、异常结束和保存失败；
- Simulator 使用受控假实现验证业务状态机，健康数据本身必须保留为未真机验证。

## 3. 羽毛球与可穿戴研究

### 3.1 单腕惯性数据的识别潜力

[Badminton stroke identification using wireless inertial sensor and neural network](https://doi.org/10.1177/17543371211048328) 收集了 6 位训练良好选手、6 种动作、3300 次重复；论文摘要报告仅使用持拍腕传感器也能在其受控数据上得到较高分类结果。

可采用的启发：

- 持拍腕是有研究依据的主要传感位置；
- 事件分割与分类应当是两个独立步骤；
- 完整时间窗口比单一峰值更有价值。

不能采用的推论：

- 该受控实验不能证明普通用户、自由打球或 Apple Watch 上具有相同表现；
- 不能把六类动作模型直接改名为本项目的“杀球/普通击球”；
- 不能只引用总体准确率，必须按测试者隔离并报告误报与漏检。

### 3.2 智能手表上的击球振动信号

[BadminSense: Enabling Fine-Grained Badminton Stroke Evaluation on a Single Smartwatch](https://arxiv.org/abs/2603.21825) 在 12 位有经验的业余选手上研究单智能手表的动作分割、分类与击球位置估计，并强调利用击球振动信号。

可采用的启发：

- 击球附近的高频冲击与振动值得保留；
- 单纯识别高速手腕运动不足以证明真实击球；
- 连续动作分割需要研究击球前后完整时序。

本项目不会因此增加击球质量评分或细分球路，因为这些属于第一版禁止范围。

### 3.3 Apple Watch 惯性数据能力的既有测量

[Accuracy and Acceptability of Wearable Motion Tracking for Inpatient Monitoring Using Smartwatches](https://doi.org/10.3390/s20247152) 使用 Apple Watch Series 3 和 5 采集约 100 Hz 三轴加速度与角速度，并与研究级 IMU 对照。

可采用的启发：

- Apple Watch 原始惯性数据具有研究使用先例；
- 不同手表代际的传感器量程可能不同；
- 量程、饱和和实际频率需要逐型号验证。

不能把旧型号论文的频率或量程直接当成第 9 系列及以后设备的事实。

### 3.4 可参考数据集

[MultiSenseBadminton](https://doi.org/10.3390/data9040049) 包含 25 位不同水平参与者、7763 次挥拍、多种传感器和视频标注，可用于理解数据组织、测试者元数据和跨水平划分。

限制：它聚焦正手高远球与反手平抽等受控动作，传感器配置与本项目不一致，不能替代自己的 Apple Watch 数据。

## 4. 杀球速度基准研究

### 4.1 初始速度定义

[Shuttlecock velocity decay after smash and slice shots in badminton](https://arxiv.org/abs/2601.01412) 显示羽毛球离拍后速度会快速衰减，且切球旋转与球种会改变衰减行为。

工程结论：

- 本项目标签必须明确对应“刚离开球拍后的初始速度”；
- 不同测量距离得到的速度不能未经模型修正直接混用；
- 外部测速记录必须保存设备、方法、配对标识和可信状态。

### 4.2 外部基准方法

[Automated Estimation of Impact Time, Impact Location, and Shuttlecock Speed in Badminton Smashes Using Event Cameras](https://arxiv.org/abs/2605.28011) 使用同步事件相机，并以高速相机方法验证击球时刻与球速。这说明可靠球速标签本身需要精确时间配对和独立参考方法。

[Reliability and validity of motion sensor and radar for measuring shuttlecock velocity in badminton](https://doaj.org/article/3c6fe7efc62a47f2ad4043f037b165fa) 比较运动传感器与多普勒雷达，进一步支持不能把腕部或球拍运动值直接视为羽毛球真实速度。

工程结论：

- 阶段 8 前必须先选定外部基准设备与配对流程；
- 手表样本、击球时刻和外部速度必须逐拍可靠对应；
- 模型输出不得写入外部真实速度字段；
- 必须报告相对于真实基准的误差分布，而不是只报告相关性。

## 5. 开源项目评估

### 5.1 Apple 官方样例

优先参考以下官方可下载样例：

- `Build a workout app for Apple Watch`：正式运动会话、实时指标和保存；
- `Building a multidevice workout app`：运动会话镜像和双向通信；
- `Transferring data with Watch Connectivity`：后台文件传输与任务完成。

这些样例与当前 SDK 关系最直接，但仍需按照本项目离线事实源、去重和研究/正式版隔离要求重新封装，不能整段复制成产品架构。

### 5.2 羽毛球开源代码

[BST-Badminton-Stroke-type-Transformer](https://github.com/Va6lue/BST-Badminton-Stroke-type-Transformer) 是基于骨架、视频和场地坐标的球路分类实现。它不适合直接用于本项目的腕部 IMU 模型，但其输入标准化一致性和数据集准备方式具有研究参考意义。

[CoachAI Projects](https://github.com/wywyWang/CoachAI-Projects) 与 ShuttleSet 面向比赛回合和未来球路预测，属于第一版明确不做的范围；不引入其模型或数据结构。

本轮没有发现一个能够直接满足“Apple Watch 持拍腕原始高频数据、离线保存、人工标签、可靠双端同步”全部约束的成熟开源项目。因此工程以 Apple 官方 API 为平台依据，以原始论文为研究依据，自建最小且可测试的数据链路。

## 6. 当前实现决策

基于上述调研，后续实现采用：

1. `CMMotionManager` 平台适配器和可注入的 Simulator 合成数据源；
2. 每条合成数据显式保存 provenance，禁止混入真机实验；
3. 独立来源时间戳、实际采样间隔和追加式文件存储；
4. Watch Connectivity 文件传输适配器与可在测试中替换的传输协议；
5. HealthKit 运动会话服务与界面分离；
6. 真实击球、分类和测速在各自实验门禁通过前只保留接口，不生成用户结果；
7. 所有算法实验采用按测试者分组的训练/验证/测试划分。

## 7. 后续查证要求

每进入一个新阶段，先核对当时 SDK 官方文档和相关原始研究。遇到以下情况必须重新检索：

- API 在当前 SDK 被废弃或行为变化；
- Simulator 与真机行为不一致；
- 目标手表型号的采样能力未知；
- 同步后台任务或 HealthKit 保存失败；
- 算法指标、数据划分或外部测速方法需要确定；
- 引入任何外部开源代码或数据集前，需要核对许可证和数据使用条件。
